## Project state

**MVP 1–5 delivered** (2026-07-31): BTS Green Line elevated 3D track over MapLibre (MVP 1), Rust GTFS preprocessor → binary cache with client-side validation (MVP 2), scheduled trains moving via a Wasm interpolation engine in a Web Worker with 1×/5×/10×/60× time-warp (MVP 3), click-to-select trains/stations with a follow-camera, train inspector, live station board and time scrubber (MVP 4), and multi-line breadth — a registry-driven, line-agnostic network of 9 simulated lines (Sukhumvit, Silom, Purple, ARL, Pink, Yellow, Gold, SRT Dark/Light Red; 155 stations, 4,481 runs), a line selector, cross-route interchange metadata, and monorail/APM/commuter vehicle models (MVP 5).

**MVP 6 delivered except MRT Orange (2026-08-02):** MRT Blue added (GTFS `route_id` 3, OSM relation 444659) — the network is now **10 lines, 193 stations, 58 patterns, 8,193 runs**, feed `20260801`. Track structure became per-OSM-way rather than per-line, so Blue renders viaduct–tunnel–viaduct for real and portals ramp instead of stepping. Underground transparency (F3.2) is in; day/night (F3.3) is driven by the *simulated clock* via a real solar-position calculation, with `auto | day | night` modes. Also shipped: floating 3D station-name labels with screen-space decluttering, a shadow-quality toggle (§3A.5), the glassmorphism UI pass, and a full responsive/touch pass across phone→desktop. `npm run verify:mvp6` (22) and `npm run verify:responsive` (54) cover all of it. **MRT Orange is not added and cannot be yet** — no OSM route relation exists to pin (see the MVP 6 implementation notes below). That is the only outstanding item.

**MVP 6's data-quality pass (2026-08-02):** the two long-standing schedule defects are fixed — MRT Blue's loop no longer produces 38 km legs (per-pattern arc selection in the preprocessor), and the feed's six zero-travel-time Blue trips no longer teleport (dwell capped so every leg has travel time). Spillover vehicles now carry their own identity so a train cannot streak across the city at the service-day rollover. `verify:kinematics` passes repeatedly instead of intermittently (16 consecutive clean runs; max displacement ~130 m over 4 s, down from ~2 km).

**MVP 5's one disclosed gap:** `npm run verify:perf` passes 4 of 5 NF1 sub-checks, not 5/5 — the sim actually ticks a meaningful number of samples during the measurement window, sim tick (p95 ~0.2–0.3 ms) and frame rate (~100 FPS) are comfortably under budget, and no frame is truncated, but the ≥300-concurrent-vehicle assertion is left **failing on purpose**: the real 9-line network's measured daily peak is 171–172 concurrent vehicles (confirmed independently by both the preprocessor's own per-minute scan and the live harness), not a bug to chase. `MAX_VEHICLES` is 1024, ~6× the measured peak, so there is real headroom; the `>=300` assertion stays as a hard gate rather than being weakened, in case a future denser network (or a bug) regresses concurrency.

The full design record is [`docs/SRS.md`](./docs/SRS.md) (versioned SRS, v1.0.0). Read §3A before writing any code that touches the MapLibre↔Three.js bridge, the Worker/Wasm boundary, or the serialization format — those decisions are deliberate and expensive to reverse.

## Implementation notes (learned in MVP 6 — underground & mixed structure)

- **Structure is per OSM way now, not per line.** `tools/track-structure.mjs`'s `deriveStructure()` reads each member way's `tunnel`/`bridge` tags; a line's registry `structure` is only the fallback for untagged ways (and its one-word UI label). This is why `fetchBranch()` does a *second* Overpass query for way tags — `out geom` returns member geometry without tags, exactly like the station-node case the file already worked around. `network.json` gained a `trackStructures[]` array parallel to `track[]`.
- **Every structure change is ramped over ~220 m by `smoothAltitudes()`, and this is not cosmetic.** Raw per-way altitudes step 33 m between tunnel (−18) and viaduct (+15) between two points ~20 m apart: the deck draws a vertical wall and a train crossing it teleports. The smoother is a distance-weighted moving average over the altitude channel only, applied to **all** lines unconditionally — on a uniform line every altitude in the window is identical so it is exactly a no-op, which is why it needs no per-line special-casing. It also gracefully handles the 2–8 point stub tunnels OSM records on ARL and SRT Red (partly-mapped underpasses): a run far shorter than the ramp never reaches full depth and becomes a shallow dip instead of a plunge that would read as a data glitch.
- **Adjacent deck meshes share their boundary track point on purpose.** `structureRuns()` emits `to === next.from`; each run is swept as its own curve, so without the shared point the tunnel deck and the viaduct deck would start a full sample apart and leave a gap at every portal. The consequence to remember when writing assertions: **a tunnel deck's bounding box legitimately reaches viaduct height at its ends** (it owns its half of the ramp), so `maxZ < 0` is not a valid "this is underground" test — `verify-mvp6.mjs` checks `minZ < -10` instead. The first version of that check failed for exactly this reason.
- **`depthTest: false`, not just opacity, is what makes see-through tunnels visible.** A tunnel at −18 m sits behind the ground plane and the building extrusions from nearly every camera angle, so merely lowering opacity leaves it fully occluded and the toggle looks broken. `NetworkLayer.setUndergroundVisible()` flips `transparent`/`opacity`/`depthTest`/`depthWrite` together.
- **Night mode repaints MapLibre's own style, it does not overlay the canvas.** The base map and the Three layer share one WebGL canvas, so any DOM overlay dark enough to read as night dims the track and trains by the same amount. `src/map/dayNight.ts`'s `NightPainter` walks the style's `background`/`fill`/`line`/`fill-extrusion`/`symbol` colour properties and blends them toward a night tint, **caching the originals on first apply and replaying them verbatim on the way back** — restoring from anything else compounds the darkening on every toggle, which `verify:mvp6` explicitly tests across repeated cycles. Colours it cannot parse (data expressions, named colours) are skipped, never guessed at. `setStyle()` was rejected as the alternative because it would tear down the custom layer — and with it the Three scene, vehicle meshes and the sim's render hook — on every toggle.
- **A subset `data:fetch` run now merges instead of truncating.** `node tools/fetch-network.mjs blue` used to write a `network.json` containing *only* the named lines, silently renumbering every `route_idx` and orphaning the committed `.tmb`. It now carries unfetched lines over from the existing file in registry order, and hard-errors if a registry line is missing from both.
- **`tools/fetch-network.mjs` is a CLI and cannot be imported.** It has a `#!` shebang (Vite's parser rejects it: "Invalid or unexpected token") and its `main()` is now guarded so it only runs when invoked directly. The pure, unit-tested helpers live in `tools/track-structure.mjs` for this reason — put new testable logic there, not in the fetcher.
- **MRT Orange has no OSM route relation to pin.** Swept live on 2026-08-02 across `route=subway|train|light_rail|monorail`, `route=construction`, and `construction:route`/`proposed:route` in the Bangkok bbox: zero candidates (the only name match is an unrelated `route=ferry` "Orange flag boat", relation 2403874). The whole pipeline sources geometry from a pinned relation id, so Orange cannot be added until one exists upstream. Do not synthesise its alignment from memory.

## Implementation notes (MVP 6 polish — labels, sun, shadows)

- **`THREE.Sprite` cannot work in this layer, and that is not obvious.** Three billboards a sprite in *view* space, but the floating-origin scheme folds MapLibre's mercator→clip matrix straight into `camera.projectionMatrix` and leaves the camera's world transform as the identity — so "view space" *is* world space and every sprite would lie flat on the ground. Station labels are plain meshes billboarded by hand against the real camera position. Anything else that needs to face the viewer has the same problem and needs the same treatment.
- **The camera's real position has to be reconstructed** (`cameraLocalPosition()` in `coordinates.ts`) from `center`/`zoom`/`pitch`/`bearing`, because `camera.position` in this layer is the origin, not the viewer. MapLibre v6 removed `getFreeCameraOptions()` and `map.transform.cameraPosition` is `@internal`, so neither is a safe source. Unit-tested against the camera model's own invariants (halving per zoom level, constant camera-to-centre distance across pitch, and the sign of the pitch offset — bearing 0 puts the camera *south* of centre).
- **Labels are sized by angle, not in metres**, so a name is about the same size on screen whether the station is 500 m or 50 km away. Two consequences that bit during development: the max-height clamp is a backstop, not a size limit (a 420 m cap silently shrank every name to a few pixels at the region-wide view), and the far fade band must be enormous (90 km) because distance is *not* what makes labels unreadable.
- **What actually keeps labels readable is `declutterStationLabels()`**, a throttled (8 Hz) screen-space pass: project, sort nearest-first with termini outranking intermediate stops, and reject anything colliding with an already-accepted box. Three bugs worth not re-introducing, all found by the harness: (1) it must read an `inBand` flag rather than `mesh.visible`, or a rejected label latches off forever; (2) it must reject `w <= 0` — a point behind the camera divides into a mirrored position that lands plausibly on screen, and those ghosts were vetoing real labels; (3) it must reject boxes entirely off-screen — near the horizon `w` goes tiny and the projected box lands thousands of pixels away at enormous size.
- **The collision box is measured along the LABEL's own up axis, not the world's.** A billboard's own axes are unforeshortened on screen; a world vertical is heavily foreshortened whenever the camera looks down, which shrank every box exactly when the map was tilted and let the dense centre pile up again.
- **Lighting follows the simulated clock** (`sunPosition.ts`, NOAA low-precision solar position). `lightingMode` is `auto | day | night`; `night` in the store is the *derived* answer, so the base-map repaint and the 3D lights always agree. The day/night boundary is civil twilight (−6°), not the horizon, and brightness/warmth interpolate so scrubbing through dawn is a sunrise rather than a switch.
- **Shadows are honestly limited and default off.** Three can only shadow geometry it owns, so this is track and trains against each other — MapLibre draws the city's extrusions in its own pass and nothing here can cast onto them without re-implementing the basemap in Three. The shadow camera is an orthographic box that follows the viewer (a network-wide frustum in a 2048² map is ~30 m per texel, i.e. useless). Because the light is directional, its *position* must be re-anchored to the moving shadow target every frame (`placeSun()`), or the frustum is left behind on the first pan. `verify:mvp6` asserts the base map still renders with shadows on, which is the real risk of running a shadow pass inside MapLibre's render loop.

## Implementation notes (language, GPS, base-map switches)

- **"Any language" splits into two problems with very different limits.** UI chrome is ours and finite (`src/i18n/strings.ts`, currently en/th/zh/ja/ko/fr/de/ru/es). Station names are *data* from OpenStreetMap's `name:<lang>` tags, and coverage is what it is — surveyed live 2026-08-02 across all ten relations: `en` 194/195, `th` 151, `zh` 27, `ja` 18, `ko` 4, `fr` 4, `ru` 2, `de` 1. So the picker is **derived from the loaded network** (`availableLanguages()`), lists each language in its own script via `Intl.DisplayNames`, and shows its real coverage percentage. Do not add a language to the picker that the data cannot serve; add it to `strings.ts` and let the derivation pick it up.
- **Coverage must be counted with the same predicate that picks the name.** `availableLanguages()` originally counted only `station.names[code]`, which reported Thai as 151/195 while all 195 labels were in fact rendering in Thai — the other 44 sit in the legacy `nameTh` field, because OSM's untagged default `name` for a Bangkok station *is* the Thai one. It now counts English and Thai through `hasNativeName()`, the predicate `stationName()` uses. A percentage in the picker is a promise about what the user will see; measure it the way the thing they see is chosen.
- **The picker shows no percentage next to the language name.** Every offered language has a fully translated interface, and a number beside the name read as "this language is 9% finished" — wrong and discouraging. Station-name coverage is a separate fact and is spelled out underneath, only when it is below 100%.
- **One language means one language.** `stationName()` returns a single string, never the old English-over-Thai pair, with a deliberate fallback chain (requested → base subtag → English → Thai → code). `hasNativeName()` distinguishes a real translation from a fallback.
- **The engine has no multilingual names and does not need them.** `StationInfo` carries only `name_en`/`name_th`; widening the binary cache would mean a format change, a Rust release and a rebuilt `.tmb` for data the frontend already holds. `localiseEngineName()` bridges by **English name, not by index** — the preprocessor drops registry-excluded stops (the Pink Line spur), so engine and `network.json` indices are not guaranteed to align, whereas the English name is copied across verbatim.
- **Label text lives in a canvas texture, so a language change rebuilds them** (`NetworkLayer.setLanguage()` → `rebuildLabels()`). That is fine — it is a user action, never per frame — but old textures must be disposed explicitly, and **`rebuildLabels()` bails out when `this.scene` is null**: calling it before `this.scene = scene` in `onAdd()` silently produced a network with zero labels, which `verify:mvp6` caught.
- **The label font stack is deliberately system-only** and Thai-first. Bundling webfonts with Thai + CJK coverage would be several megabytes against NF2's 5 MB budget, and system faces render Thai better anyway. The canvas box adds half a line of leading because Thai stacks vowels and tone marks well outside the Latin cap height — a tight box clips them. Long names wrap to two lines (`wrapLabel()`), word-wrapped where there are spaces and split near the middle for scripts that don't space words.
- **Geolocation is opt-in and must stay that way.** Nothing touches `navigator.geolocation` until the locate button is pressed; prompting on load is how an app gets permanently denied, and `verify:ux` asserts it. It uses `watchPosition` (the browser pushes updates and the OS batches GPS wake-ups) and `dispose()` on unmount, or the location hardware stays awake after the component is gone. The accuracy halo is a **metre-radius GeoJSON polygon**, not a pixel-radius `circle` layer — accuracy is a distance, and a pixel circle would misrepresent it at every zoom.
- **The 3D-buildings switch matches layers by TYPE (`fill-extrusion`), never by id** — style authors rename layers, and a style with no extrusions should have nothing to toggle rather than throw.
- **MRT Blue's loop needed a per-pattern arc choice, and that is now how every route works.** The Blue Line serves Tha Phra twice (once on the circle, once on the Lak Song arm) but `network.json` gives each route a single stitched polyline, so snapping a stop to its *nearest* arc position put 9 schedule legs the wrong way round the circle — **Tha Phra ↔ จรัญฯ 13 measured 38.3 km against a scheduled 150–180 s**, a train sliding the length of the line at ~900 km/h. Fixed in the preprocessor: `spline::snap_candidates()` keeps **every** position on the polyline that comes within the stop's own snap distance (+`CANDIDATE_SLACK_M`, 40 m) rather than only the nearest, and `choose_pattern_arcs()` runs an exact DP per trip minimising `Σ|Δarc|` over the whole stop sequence. Only the sequence can say which way round a loop a train goes, which is why the choice cannot be made per stop. Nothing about the cache format changed — `PatternStop` already carried its own `arc_m`, and `world.rs` moves trains from that, not from the station's — so the station list, its ordering and `station_idx` are all untouched. Almost every stop has one candidate, so this is linear in practice.
- **The feed publishes 6 MRT Blue trips with zero travel time between stations, and they had to be repaired, not passed through.** Trips 5285, 7869, 7870 and 7874–7876 list every stop as `arrival = 60i, departure = 60(i+1)` — a 60 s dwell and a **zero-second** ride — putting 26 stations and 47 km inside 25 minutes. `eval_pattern`'s `denom > 0.0` guard turns that into `p = 1.0`, so the train stands still and then teleports 1.4 km the instant the dwell ends; sampling either side of that boundary is what made `verify:kinematics` fail intermittently after the loop fix. The preprocessor now caps a dwell at `MAX_DWELL_BEFORE_ZERO_LEG_S` (20 s) whenever the published one would run right up to the next arrival — 145 stops across the feed. **Arrival times are never touched**: they are what a rider reads off a board, and the dwell is the least load-bearing number in the row. This does not make the trip physically possible (nothing can — the feed's own total is impossible), it makes the train move between the stations instead of jumping. The count is reported as `zero_travel_legs_repaired`.
- **`network.report.json` now carries `max_leg_kmh` / `implausible_legs`**, every leg whose arc length over its scheduled running time exceeds 200 km/h. This is the number that exposed the loop defect, and having it in the build output means the next data problem of this shape is visible immediately rather than only as an intermittent kinematics failure. Two legs remain over the threshold: ARL Suvarnabhumi → Lat Krabang at 306 km/h (5.09 km in a published 60 s), on both ARL express trips. That is the feed's own arrival times, not a snap — do not "fix" it by inventing a different schedule.
- **A vehicle's identity is `run_idx` *plus a service-day tag*, not `run_idx` alone.** The engine also evaluates the previous service day at `sec+86400` for post-midnight spillover, and around the rollover both copies of a run can be live at once at opposite ends of the line. Everything downstream matches vehicles across frames by lane 5 — the render-side lerp, selection, the follow camera — so sharing one id made a train streak across the city whenever the two copies swapped in and out. `world.rs` now adds `SPILLOVER_RUN_TAG` (1 << 20, far below f32's 2^24 exact-integer limit) to the spillover copy's lane 5, and `vehicle_run_idx()` strips it again for schedule queries — `run_detail` masks its argument, since the UI hands back whatever the buffer carried.
- **`verify-kinematics.mjs` prints raw frame poses next to interpolated ones when it fails**, because "a train moved 1.6 km in 4 s" has more than one cause and the first question is always whether the engine produced it or the render-side lerp did. It also skips run ids that appear twice. The engine also evaluates the previous service day at `sec+86400` for post-midnight spillover, so around the rollover one run can be live twice at different points on its line; matching those by id alone paired one sample's copy with the other's and reported a 2 km displacement in four seconds. That was the source of this check's intermittent failures, not a teleporting train.

## Implementation notes (rolling stock & train visibility)

- **Trains are geometry built in code, not a `.glb`.** A few hundred triangles per fleet is all these camera distances can resolve, and generating them keeps the app inside NF2's 5 MB budget with no asset pipeline, no licence to track and no loading state. It also lets each consist take its route's livery at build time, which one shared model file could not do without a material swap per route.
- **`ExtrudeGeometry` needs TWO rotations to stand a car upright**, and getting it wrong fails quietly. A vertex arrives as (profileHorizontal, profileVertical, alongCar); `rotateY(+90°)` alone yields (alongCar, profileVertical, −profileHorizontal) — the car lies on its side with width and height swapped. `rotateY(+90°)` then `rotateX(+90°)` is the correct mapping. The footprint test (bounding box vs. `consistLengthM`, and `min.z >= 0`) is what caught both this and the next one.
- **`bodyShell` anchors at the car's START, not its centre.** The extrusion already runs 0→depth along its own axis, so translating by a centre pushes every shell half a car ahead of the boxes that trim it — which made a "65 m" consist measure 69 m.
- **`mergeGeometries` returns null, silently, when inputs disagree about indexing.** This model mixes `BoxGeometry` (indexed) with `ExtrudeGeometry` (not), so `paint()` normalises everything to non-indexed on the way through — one place, so a new kind of part cannot break the merge later.
- **Train visibility is a two-stage problem and only the second stage actually works far out.** Enlarging the mesh (`setViewScale`, capped at 6×) covers the middle distances. Past ~7 km it stops helping: a train scaled to stay visible lengthwise is still a metre or two wide, so it renders as a hairline lying exactly along the track and is indistinguishable from the track. Beyond that the manager draws **one camera-facing dot per train** in the line's colour, angular-sized like the station labels. That is what makes the whole-region view — the view the app opens at — answer "where are the trains right now?". Hidden routes are skipped so the line filter means the same thing at every zoom.
- **Camera distance for scaling is altitude / cos(pitch), not distance from the local origin.** The origin is Siam, so an origin-relative distance would enlarge trains over Bang Na while zoomed right in.

## Implementation notes (onboarding, privacy, discoverability)

- **There is no cookie banner because there is nothing to consent to, and that is a promise the code has to keep.** The app sets no cookies, loads no analytics, has no accounts and embeds no third parties. `src/lib/preferences.ts` stores only user-chosen view settings in `localStorage`, which is exempt from consent under both ePrivacy ("strictly necessary for a service explicitly requested by the user") and the PDPA. `verify:ux` asserts `document.cookie` is genuinely empty. **If analytics or any third-party script is ever added, that exemption is gone and a real consent flow becomes mandatory** — and the About panel's privacy text becomes a false statement, which is worse than no statement.
- **Preferences are read synchronously at module load** (`const stored = loadPreferences()` in the store), not applied in an effect. An effect would let the map build its label textures in the wrong language and rebuild them a frame later — visible and wasteful. Persistence is a single `useAppStore.subscribe` at the bottom of the store, so there is one place to audit what gets written.
- **The tour spotlights real elements, and that is why it is anchored by selector.** Each step names a `[data-tour="…"]` value; the scrim is ONE element sized to that target's rect carrying a `0 0 0 9999px` box-shadow, which darkens everything outside it — no SVG mask, no four-rectangle jigsaw to keep in sync, and it animates between steps because only position and size change. Steps whose control is missing fall back honestly: no hole, centred card, no arrow pointing at nothing.
- **The tour's arrow is dark with a white rim, not white.** It spends most of its life overlapping the brightly lit cut-out it points into, where a white arrow is invisible; it also has to read against the dim scrim. Both, or neither.
- **A full-screen catcher blocks clicks during the tour.** The spotlight's hit area is only the hole (the darkening is a shadow, not an element), so without the catcher the dimmed region still passed clicks to the map and a stray tap opened a train inspector over the thing being pointed at. **Consequence for the harness: every verify script must seed `{"tourSeen":true}` into `localStorage` via `evaluateOnNewDocument`**, or its synthetic clicks hit the tour instead of the app — this is exactly what broke `verify:camera` and `verify:mvp4` when the catcher landed.
- **A target inside a scroll container must be scrolled into view BEFORE it is measured.** Several targets live in the left panel's `overflow-y-auto` list, and `getBoundingClientRect()` cheerfully reports the position of an element that has been scrolled out of it — which drew the spotlight over an empty strip at the edge of the panel with an arrow pointing at nothing. `measure()` calls `scrollIntoView({ block: "nearest" })` first, then falls back to a centred card if the rect is still off-screen.
- **The measure loop re-runs for ~3 s after each step, not once.** Two things move under the highlight: a camera animation, and targets that appear asynchronously — the "tap a train" step spotlights the inspector, which only exists once the engine has answered the selection query.
- **Steps that describe the map DO the thing.** "Tap a train" flies to a live, moving vehicle, selects it, and highlights the inspector that opens; "move the camera" actually orbits; the underground step drops onto the Blue Line's tunnelled core. A step that says "tap a train" over a city-wide view where a train is two pixels teaches nothing. `showcaseTrain()` returns false when no vehicle is live (engine not ready, or 03:00) so the step degrades to a plain card rather than pointing at a panel that never arrives.
- **The tour needs the map, so `src/map/activeMap.ts` publishes it** — a module ref mirroring `activeSimClient`, for the same reason: the map is an imperative object, not UI state, and putting it in the store would re-render every subscriber on remount.
- **The tour demonstrates rather than points, and cleans up after itself.** Steps carry an optional `apply()` that actually turns on see-through tunnels and night mode; `finish()` reverts them and clears any selection. If you add a step that changes state, revert it there too — leaving a visitor with settings they never chose is the failure mode this design guards against.
- **Panel expansion lives in the store (`panelExpanded`), not in LineSelector.** The tour has to open the panel before it can spotlight a control inside it, and a highlight anchored to an element that is not rendered has nothing to point at. `null` still means "follow the viewport".
- **`?lang=` outranks the saved preference.** It is what the sitemap's hreflang alternates point at, so a Thai search result must open in Thai even for a returning visitor whose last choice was English. Order is URL → stored → `navigator.languages` → English.
- **`src/i18n/documentLanguage.ts` keeps `<html lang>`, `<title>` and the canonical `?lang=` in step**, outside React, because they are document-level concerns no component owns. It uses `replaceState`, not `pushState`: switching language is not a navigation and must not fill the back button.
- **Translations are `Partial<Strings>` with per-key English fallback, and `tools/i18n.test.mjs` keeps every table complete.** The fallback means a missing string is invisible at runtime — the app just shows English — which is right for users and exactly wrong for maintenance, so the gap is caught in tests instead. All nine languages are currently complete. The suite also fails a table that is more than half identical to English (an unfinished placeholder), a tour body too long for the 340 px card, and a control word too long for its fixed-width button.
- **`index.html` carries real prerendered content inside `#root`.** A WebGL SPA is an empty div to a non-rendering crawler and to most link unfurlers; React replaces this on mount. `tools/seo.test.mjs` asserts it stays substantial and that the hreflang list, sitemap and manifest do not drift from `UI_LANGUAGES`. The JSON-LD deliberately claims **no** `aggregateRating` or `review` — inventing either is structured-data spam and risks losing rich results entirely.
- **`npm run og:image` regenerates `public/og-image.png` from the running app** at exactly 1200×630 with all UI chrome hidden. A hand-drawn card would drift from reality the first time anything changed.
- **Donation links are empty by default and the Support UI hides itself when they are** (`src/config/support.ts`). A payment destination is an account only the owner can supply; guessing one sends real money to the wrong person. PromptPay is shown as copyable text, never as an app-generated QR — a QR the page draws is indistinguishable from one an attacker swapped in.

## Implementation notes (responsive / touch — read before touching any component)

- **Size touch targets by `pointer-coarse:`, never by the `sm:` breakpoint.** This is the mistake the responsive harness exists to catch, and it caught it: an iPad is 768–1024 px wide, so width-keyed rules gave it the 24 px mouse-sized rows and 28 px close buttons meant for a laptop, on a device where every target is a fingertip. Viewport width answers "how much room is there"; `pointer-coarse` answers "is this a finger". Use the breakpoint for layout, the pointer query for hit areas.
- **`useIsCompact()` / `useIsShort()` (`src/hooks/useMediaQuery.ts`) are for STRUCTURE, not styling.** Anything that is only a different look is a Tailwind breakpoint. The hooks exist because the line panel's *default open state* differs by device, which CSS can't express. `COMPACT_QUERY` is deliberately pinned to Tailwind's `sm` so JS and CSS never disagree about where the layout changes. They use `useSyncExternalStore` so the first render is already correct — a `useState`+`useEffect` version flashes the desktop layout for a frame on a phone.
- **A landscape phone is a *short* viewport, not a narrow one** (844×390 is wider than `sm`). Anything that assumes "small screen == narrow" leaves a bottom bar and a full line list eating 60% of the height. `useIsShort()` (max-height 520 px) collapses the line panel there, and the feed-provenance line is hidden by a height query as well as the width one.
- **The line panel is capped at `70dvh`, not `100dvh - margin`.** With fingertip rows, ten lines plus the view toggles is ~700 px, which filled 91% of an iPad in landscape. It scrolls internally instead.
- **The detail panel is one component** (`OverlayPanel`), used by both `TrainInspector` and `StationBoard` — they are the same slot in the interface (mutually exclusive by construction: selecting a train clears the station) and must not drift apart. It is a bottom sheet under `sm` and a floating card above. The sheet deliberately covers the bottom time controls; closing it brings them back, so nothing becomes unreachable.
- **Touch orbiting does not go through `cameraControls.ts`'s mouse bindings.** `map.dragRotate.disable()` there does NOT disable `touchZoomRotate` (pinch/twist) or `touchPitch` (two-finger vertical drag), which are separate handlers and the only way to rotate on a device with no middle button, right button or ctrl key. They are enabled explicitly so a future change to the mouse policy cannot silently take rotation away from every phone and tablet.
- **`touch-action: none` on the MapLibre canvas (`index.css`) is load-bearing**, not a nicety: without it a drag-pan also rubber-bands the page and a two-finger pitch triggers the browser's pinch-zoom instead of the map's.
- **`npm run verify:responsive` measures the laid-out DOM, not class names** — a Tailwind class that doesn't exist silently does nothing and would pass any markup-based check. It sweeps 7 viewports (320→2560 px, both phone orientations, both tablet orientations) asserting no page overflow, the canvas fills the viewport, no control escapes the viewport, the panel collapses only where it should, targets are ≥32 px on touch, and the detail panel takes the right shape. 54 checks.

## Implementation notes (search & journey planner)

- **The planner's graph node is a *platform*, `(routeIdx, stationIdx)`, not a station.** "Change at Asok" then falls out of Dijkstra on its own — a ride edge joins consecutive `station_idx` on one route, a transfer edge joins two platforms the engine already links as interchanges. `TRANSFER_PENALTY_S` is 300 s, deliberately generous: for the newcomer this is built for, one fewer change beats five minutes saved.
- **Hop times come from the published timetable, not from distance.** `sampleHopTimes()` asks the engine for one representative run per route (`station_board` → `run_detail`) and reads its stop-to-stop deltas; it is built lazily the first time the planner is opened, off the frame path. It deliberately returns *partial* data — a route with no live run at the current clock simply gets no entry and `hopSeconds()` estimates it — because failing the whole plan over one shut line would be worse than an approximate leg.
- **Search indexes every name a station has, in every language, regardless of the UI language.** The person searching has a name from a hotel booking or a sign and no idea which line it is on; someone reading the Japanese UI who types "Asok" must still find アソーク駅. Matching is substring-on-normalised, not edit-distance fuzzy — a similarity score over 195 short proper nouns in six scripts mostly produces confident nonsense. `normalise()` strips Latin combining marks but **not** Thai vowels or tone marks: removing those changes the word rather than normalising it.
- **Results are one row per place, not one per platform** — otherwise a two-line interchange pushes everything else off a short list. Interchanges are promoted *within* a match tier, never across one: a prefix match on a single-line stop still beats a mid-word match on an interchange.
- **`data-panel="planner"` exists because the station board is also a `role="dialog"`.** A bare `[role=dialog]` lookup in a harness lands on whichever is open, and the first version of `verify:planner` "passed" its language assertions against the station board's text.
- **Puppeteer reloads the page when `hasTouch` changes**, which resets the store — so the phone-viewport check in `verify:planner` opens the planner *after* the resize, not before. A triple click also does not select the contents of an `input[type=search]` here; use Ctrl+A, or every search after the first runs against the concatenated query.

## Implementation notes (payments, media)

- **A payment QR is the one place in this project where a wrong byte moves real money**, so the payload lives in one small pure module (`src/lib/promptpay.ts`) with the CRC-16/CCITT-FALSE check vector pinned in a test, and `normaliseMobile()` **throws** on anything that is not ten digits starting with 0 rather than truncating or padding. The number originally supplied for this project had eleven digits; guessing which digit to drop would have produced a QR addressing somebody else's wallet, so it was queried instead of inferred.
- **The QR is rendered at build time and committed, never drawn by the page.** `npm run promptpay:qr` writes `public/promptpay-qr.svg`, so what a visitor scans is a reviewable file in the repository, and the account digits are always printed beside it. `qrcode` stays a devDependency, so the browser bundle pays nothing for it. The payload is static — no amount tag — so the payer chooses what to send.
- **`docs/media/` is a build output that happens to be committed.** Do not hand-edit it; change `tools/make-media.mjs` or `tools/make-video.mjs`. The three rules worth not re-learning: the simulated clock must be pinned (or the gallery differs on every regeneration and its diff means nothing), each shot must wait on `map.loaded() && map.areTilesLoaded()` rather than a fixed sleep (a 3 s sleep produced a hero image of the 3D network floating over a blank page), and the street-level shot must be framed from the vehicle buffer rather than from a landmark (aiming at Siam and hoping produced a lovely photograph with no train in it).
- **Video pacing comes from each frame's own CDP timestamp**, not from an assumed frame rate: `Page.screencastFrame` delivery is bursty, so a fixed-fps assembly speeds up and slows down against reality. Frames go into an ffmpeg concat list with real durations and are resampled to constant 30 fps. The caption overlay is re-created on every call because a version that installed it once died four scenes into a 91-second recording.

## Implementation notes (learned in MVP 1 — read before touching the map/3D code)

- **Floating origin lives in `src/map/coordinates.ts`** — all Three geometry is built in a local east/north/up meter frame around Siam (`ORIGIN_LNG_LAT`); `ThreeLayer.ts` folds the float64 origin translation + mercator meter scale into the camera projection matrix each frame. Never put absolute mercator values into vertex data.
- **MapLibre's stylesheet forces `.maplibregl-map { position: relative }`**, overriding Tailwind's `absolute` on the container — size the map container with `h-full w-full`, not `absolute inset-0`, or it collapses to 0 height (silently: you get a 300px default canvas and a blank map).
- **Metric-width geometry disappears at low zoom.** The 9 m track deck is subpixel below ~z13, so each branch also gets a constant-pixel-width `Line2`/`LineMaterial` centerline (`buildTrackLine`); its `resolution` uniform must be updated per frame in `ThreeLayer.render()`.
- **Base map is OpenFreeMap's Liberty style** (`https://tiles.openfreemap.org/styles/liberty`) — vector tiles, free, no API key, includes 3D building extrusions that correctly depth-occlude the track.
- **Data provenance:** track geometry = OSM route relations 444651 (Sukhumvit) + 2067854 (Silom) via Overpass, ODbL; station coords = Namtang GTFS `route_id` 1 & 2, CC-BY 4.0. Both attributions render in the map's attribution control — keep them.
- **maplibre-gl is on v6.** The v4→v6 migration touched four things, all load-bearing: `render()` now takes `(gl, options)` and the mercator→clip matrix comes from `options.defaultProjectionData.mainMatrix`; there is **no default export** (named imports only); GL context flags moved from `MapOptions` into `canvasContextAttributes`; and v6 locates its tile worker via `new URL(\`./${name}\`, import.meta.url)` — a dynamic specifier no bundler can rewrite, so `MapContainer.tsx` must call `setWorkerUrl()` with a `?worker&url` import. **Without that call the base map goes silently blank** (style loads, tiles never parse) while the Three layer keeps drawing — so a screenshot that shows track but no buildings means the worker URL broke.
- **Camera input is custom** (`src/map/cameraControls.ts`) — it calls `map.dragRotate.disable()` and owns rotation entirely. Middle-drag, right-drag and ctrl+left-drag all **orbit**: vertical pitches, horizontal turns, applied together in one `jumpTo` so a diagonal drag does both. Directions and rates match MapLibre's (`-0.5 * dy`, `+0.8 * dx`); the reasons for replacing `dragRotate` rather than using it are that it has no middle-button binding and its rotation is anchored to the press point, so bearing response varies with where you clicked. Pan and scroll-zoom are left to MapLibre untouched. Verify with `npm run verify:camera`.
- **Click jitter can get misclassified as a drag.** MapLibre's default `clickTolerance` (3px) is how it tells a click from a drag-pan; ordinary pointer jitter between mousedown/mouseup can exceed that, firing `dragstart`. `MapContainer.tsx`'s `onDragStart` unconditionally drops `following` on any pan (so a real user drag hands control back — see `followCamera.ts`), so a misclassified click silently cancelled follow-camera on the very next click after engaging it. `MapContainer.tsx` sets `clickTolerance: 6` on the `MapLibreMap` constructor to absorb normal jitter; don't revert it as unused-looking noise. It's a mitigation, not a guarantee — a trackpad or touchscreen tap can still exceed 6px.

## Implementation notes (learned in MVP 2/3 — engine & pipeline)

- **`docs/ENGINE_CONTRACT.md` is the interface spec** for the cache format, stride-8 `Float32Array` vehicle buffer, worker protocol, and wasm API. Update it when any of those change — it's what keeps the Rust and TS sides in sync.
- **The Namtang feed is frequency-based for BTS**: routes 1/2 have 14 trip *patterns* with relative `stop_times` (starting 00:00:00) expanded via `frequencies.txt` headway windows (06:00–24:00). The preprocessor (`rust-engine/preprocessor`) expands them into ~2,162 concrete runs. Service 1 = weekdays, 2 = weekends, with 42 Thai-holiday `calendar_dates` exceptions.
- **MapLibre's earth radius is 6371008.8 m** (`src/geo/lng_lat.ts`), NOT the WGS84 circumference — `sim-core/src/geo.rs` replicates MapLibre's exact math so Rust ENU output matches `src/map/coordinates.ts` to sub-millimeter (unit-tested). Don't "fix" it to 40075016.686.
- **Engine positions are a pure function of time** (no integration): worker evaluates at 10 Hz into pooled transferable buffers (3-buffer ping-pong, never allocates on the frame path); `SimClient.getInterpolated` lerps the two latest frames matched by `run_idx`. Per-frame data never touches React/Zustand.
- **Schedule metadata is engine-side, not TS-side** (`sim-core/src/query.rs`, contract §7). The vehicle buffer carries pose only; headsign/ETA/origin/destination/station boards come from `run_detail`/`station_board` over a promise-based worker query channel. They are UI-rate (on selection, ~1 Hz) — putting one on the frame path re-introduces exactly the boundary cost §3A.2 exists to avoid. The TS mirrors in `protocol.ts` keep serde's snake_case verbatim; rename a field in Rust and the UI breaks silently unless both move together.
- **Trains are one draw call per route**: one merged vertex-colored geometry per route in `VehicleManager` (InstancedMesh, capacity `MAX_VEHICLES` = 1024 as of MVP 5 — was 512 through MVP 2–4, raised ahead of the 9-line network so a real peak is never silently truncated). That was "2 draw calls total" when the network was Green Line only (Sukhumvit + Silom); it is N draw calls for an N-line network now — still one per route, never one per train (SRS §3A.5).
- Bangkok time = UTC+7 fixed (no DST); the worker splits `simEpochMs + 7 h` into `date_yyyymmdd` + `sec_of_day` via UTC getters, and the engine also evaluates the *previous* service day at `sec+86400` for post-midnight spillover.
- Kheha (stop 13608) snaps 63.9 m from the OSM track end — genuine terminus geometry offset, under the 150 m hard limit; every other stop snaps < 40 m.

## Implementation notes (learned in MVP 5 — multi-line breadth)

- **The registry-index invariant is the load-bearing contract of the whole line-agnostic pipeline.** `tools/lines.config.mjs`'s `LINES` array order == `src/data/network.json` `lines[i]` order == the Rust cache's `CacheDoc.routes[i]` order == vehicle-buffer `route_idx` (lane 6) == `VehicleManager`'s per-route `InstancedMesh` index. It is enforced at three independent points: `assertRegistryValid()` (duplicate keys/route-ids, unknown structure/vehicleType, malformed color/id-list fields), a Rust preprocessor test (`route_order_follows_network_json_line_order`), and the fact that nothing anywhere hardcodes a route index or name — `fetch-network.mjs`, the preprocessor, and the frontend all just iterate whatever `LINES`/`network.json` contains. Appending a line is safe; reordering or removing one invalidates every committed `.tmb` and desyncs `route_idx` across the whole stack.
- **The track-only route path (`gtfsRouteId: null`) is a real, tested mechanism, not a stub.** A line entry with no GTFS route id renders (track + stations from its own `network.json` data) but never simulates (`RouteDoc.simulated = false`, no patterns, no runs, `station_board`/`run_detail` return an empty board rather than erroring — see `sim-core/src/query.rs` tests `a_track_only_route_has_an_empty_board_not_a_missing_one` / `..._still_reports_its_stations`). **No line in the current registry actually uses it** — all 10 entries in `LINES` have a real `gtfsRouteId` and are fully simulated. MRT Orange, the intended first user of this path, is still not in the registry, and as of MVP 6 the blocker is geometry rather than scheduling: OSM has no route relation for it to pin (see the MVP 6 notes). Don't read "10 lines rendered" as "10 simulated plus track-only ones" — right now those are the same 10.
- **Interchange metadata is auto-linked within 300 m, plus a manual override list for what that radius can't reach.** The preprocessor's `link_interchanges()` (called with `INTERCHANGE_RADIUS_M = 300.0`) pairs any two different routes' stations within 300 m of each other, symmetric, never self-referential. `INTERCHANGE_OVERRIDES` in `tools/lines.config.mjs` (fed through as `TrackFile.interchange_overrides`, GTFS stop-id pairs) covers walkways/platforms the radius genuinely can't see — currently one entry: Purple↔Pink at Nonthaburi Civic Center, whose two platforms are ~555 m apart but share the same GTFS `stop_id` "359" on both sides (verified against OSM node tags, see the long comment on the `pink` registry entry), so the override pairs `["359", "359"]` — safe because no other route uses that stop id, so it can only ever resolve to Purple's copy and Pink's copy of it.
- **A registry line's `gtfsRouteId: Some(id)` doesn't guarantee frequency-based expansion.** The Namtang feed mixes both GTFS shapes: BTS-style routes (Sukhumvit, Silom) are frequency-based (relative `stop_times` + `frequencies.txt` headway windows); other operators (ARL, SRT Red, etc.) publish concrete absolute departures with no `frequencies.txt` rows for their trips at all. `runs_for_pattern()` in the preprocessor handles both: a trip with frequency rows expands into one run per headway slot, a trip with none becomes exactly one run starting at its own first stop's arrival time. A trip with neither shape is a hard error, never a silent zero-run drop.
- **`window.__map.getLayer("network-3d")` does not hand back the `NetworkLayer` instance directly.** MapLibre wraps every added layer in its own style-layer object; the `CustomLayerInterface` you passed to `addLayer()` — and its Three `scene` — lives on `.implementation`. Needed this to reach real rendered `InstancedMesh` geometry from a verify script (`tools/verify-mvp5.mjs`) rather than trusting the `ConsistSpec` config table alone.
- **`StationBoard.tsx`'s "Interchange" label and its transfer chips render inside a `uppercase`-styled heading** — `document.body.innerText` reflects the CSS text-transform, so a verify script comparing against the literal string `"Interchange"` (mixed case) silently never matches; compare case-insensitively, same gotcha `verify-mvp4.mjs` already documents for "next departures".

## What this project is

Greater Bangkok Metro Mini 3D is a web-based 3D visualization of Bangkok's rail transit network (BTS, MRT, SRT, Airport Rail Link), inspired by Mini Tokyo 3D. Trains are placed on 3D track by **interpolating static GTFS timetables** — there is no live vehicle feed (GTFS-Realtime is explicitly out of scope for v1.0). The app lets a user scrub to any past/future time and see where trains *should* be per schedule.

## Planned architecture (from the SRS)

The system is three layers plus an offline pipeline:

1. **Data pipeline** (`tools/gtfs_preprocessor/`, Rust CLI) — converts a GTFS ZIP feed into a compact binary cache (target: **< 3 MB compressed**), falling back to OpenStreetMap geometry where `shapes.txt` is coarse or missing. This is offline/build-time only; scraping (if ever used as a fallback) belongs here, never in client runtime.
2. **Simulation core** (`rust-engine/`, Rust → WebAssembly via `wasm-pack`) — parses the binary cache and computes vehicle kinematics. Runs inside a Web Worker, decoupled from the render frame rate (fixed-timestep sim tick; render side interpolates between the two latest sim states).
3. **Frontend** (`src/`, Vite + TypeScript + React 19 + Tailwind + Zustand) — MapLibre GL JS base map with a custom `CustomLayerInterface` WebGL layer that hosts a Three.js scene for 3D track/train rendering.

### Load-bearing design decisions (SRS §3A) — do not casually deviate

- **Worker↔main-thread transfer:** use **transferable `ArrayBuffer`s** via `postMessage`, not `SharedArrayBuffer`. Avoids the COOP/COEP cross-origin-isolation requirement entirely (many static hosts, e.g. GitHub Pages, can't set those headers). Only reconsider `SharedArrayBuffer` if profiling proves transfer overhead matters, and only after confirming header support on the deployment target.
- **Wasm↔JS API shape:** the engine should expose "tick(time) → fills a shared flat `Float32Array`" (one buffer, zero-copy read), not per-vehicle getter calls — the JS↔Wasm boundary crossing, not the math, is the actual bottleneck against the 3 ms/frame budget.
- **Rendering:** use Three.js `InstancedMesh` per vehicle type (one draw call per type), not one mesh per train.
- **Coordinate precision:** adopt a floating-origin / camera-relative coordinate scheme from the start (MVP 1), not as a retrofit — absolute mercator coordinates at city scale cause visible `float32` jitter, especially in follow-camera.
- **MapLibre↔Three bridge:** both must share the *same* WebGL context (don't let Three create its own canvas). Positions go through `MercatorCoordinate.fromLngLat()`; depth/occlusion between MapLibre terrain and the Three layer is the hard part of underground transparency (F3.2) — budget real time for it. `deck.gl` + `MapboxOverlay` is the documented fallback if the bridge becomes a time sink.
- **State ownership:** Zustand holds only UI-derived state (selected train, line filters) — per-frame kinematics must never enter React state, or re-renders thrash.
- **Serialization:** evaluate `rkyv` (zero-copy deserialization) for the binary cache before falling back to Bincode. Reserve MessagePack/Protobuf for any interchange boundary that isn't Rust-to-Rust.
- **Track geometry:** 3D coordinates `[lon, lat, altitude_meters]`; altitude by structure type — underground −12 to −25 m, at-grade +0.5 m, elevated +12 to +22 m. Apply Catmull-Rom/Bézier spline smoothing so curve nodes don't produce abrupt heading changes.
- **Motion model:** status per vehicle at time *t* is dwell / in-transit / inactive based on scheduled arrival/departure times; in-transit progress uses the smoothstep ease `3p² − 2p³` for accel/decel, with heading derived from the track's 3D tangent (see SRS §F2.1–F2.2 for the exact formulas).

## Delivery model — build in this order

The project is scoped as **vertical MVP slices**, not horizontal layers (data → engine → UI). Each MVP is a complete, demoable increment; later MVPs assume earlier ones are done. If asked to implement a feature, place it in the right MVP rather than building ahead of it:

## Transit coverage & operator status

Nine lines are in scope (BTS Green [Sukhumvit + Silom], MRT Blue, MRT Purple, SRT Red, Airport Rail Link, MRT Pink, MRT Yellow, BTS Gold, MRT Orange). Seven of the nine (everything except MRT Blue and MRT Orange) are in the registry and fully simulated as of MVP 5. **MRT Orange is pre-revenue and gets track geometry only** — no simulated trains, and it isn't even a registry entry yet (deferred whole to MVP 6) — until it has a published operational schedule. **MRT Blue remains unverified/unbuilt**, still scoped to MVP 6. The rest of the operational/pre-revenue classification was **re-verified against current sources on 2026-07-31** (SRS §2's caveat block, MVP 5 Task 11): MRT Orange is still pre-revenue (Eastern Section now projected late 2027, Western Section ~2030); the Pink Line's Muang Thong Thani spur has been in full revenue service since 2025-06-17 but is deliberately **not** in the registry (its trips share Pink's main `gtfs_route_id`, and its own OSM relation pair is a separate out-of-scope fetch); MRT Purple's southern extension (Tao Poon–Rat Burana) is still under construction, not open. Re-check again before public release if meaningfully more time has passed.

## Non-functional targets worth knowing before optimizing

- 60 FPS desktop / 30+ FPS mobile; Wasm sim tick < 3 ms/frame for up to 300 concurrent active vehicles. **As of MVP 5** (`npm run verify:perf` against the full 9-line network, production build): sim tick p95 ≈ 0.2–0.3 ms and ~100 FPS both comfortably clear the target, but the 300-concurrent-vehicle scale target is not yet reached — the real network's measured daily peak is 171–172 vehicles (`public/data/network.report.json`'s `peak_concurrent`), a real GTFS-density fact about these 9 lines, not a performance bug. `MAX_VEHICLES` is 1024 (~6× that peak), so there's headroom for MVP 6's remaining lines; the `verify:perf` assertion is left failing on purpose rather than weakened or gamed with synthetic load (4/5 sub-checks pass; only peak-concurrency fails). **Updated at MVP 6** (`npm run verify:perf`, production build, 10-line network): adding MRT Blue — 24 patterns and 3,712 of the network's 8,193 runs, the busiest line in the feed — moved the preprocessor's full-day per-minute peak to **246** concurrent vehicles (weekday 2026-07-22 19:30; weekend 212). Sim tick p95 rose from ~0.2–0.3 ms to **1.20 ms** (mean 0.53 ms) — still comfortably inside the 3 ms budget — and frame rate is **130 FPS**. Still 4/5: the ≥300 gate remains the one failure, and is now unlikely ever to pass, because the only in-scope line left is MRT Orange, which is pre-revenue with no timetable at all. `MAX_VEHICLES` (1024) is ~4× the new peak, so nothing truncates. **Note the harness reports a lower peak (197) than the report's 246** — they measure different things and no longer coincide as they did at MVP 5: the report is an exhaustive per-minute scan of the whole service day, while the harness samples live over a short window at the reported peak minute and catches whatever is active during it. Quote the report for "how dense is this network" and the harness for "what did the running sim do".
- Initial bundle ≤ 5 MB compressed (including the binary timetable); GLTF models lazy-load with LOD. **As of MVP 5:** gzipped `dist/` + `network.tmb` totals ≈ 0.85 MB, well inside budget.
- Browser matrix: Chrome 90+, Safari 15+, Firefox 88+, Edge (Chromium) — WebGL 2.0 + WebAssembly baseline.
- OpenStreetMap-derived geometry requires ODbL attribution; any scraped fallback data must respect the source's ToS and is preprocessor-only, never live in the client.
