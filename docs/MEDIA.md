# Media

Every image and the video in this repository are **generated from the running
app**, not captured by hand. `docs/media/` is therefore a build output that
happens to be committed — treat it that way.

The reason is drift. A hand-captured screenshot is accurate on the day it is
taken and slowly becomes a picture of software that no longer exists; nobody
notices, because nobody re-reads the README. A generated gallery can be
regenerated in one command, so it is cheap to keep honest.

## Regenerating

Both scripts drive the real app over the dev server, so start that first:

```bash
npm run dev
```

Then, in another shell:

```bash
npm run media        # docs/media/*.png — the README gallery
npm run media:video  # docs/media/demo.mp4 and demo.gif
```

`npm run media:video` additionally needs **ffmpeg** on `PATH`.

## Why the shots look the way they do

- **The simulated clock is pinned** to Wednesday 17:40 — a weekday service
  pattern at the evening peak, which is both the busiest moment in the feed and
  in daylight. Without pinning, the gallery would differ every time it was
  regenerated (different time of day, different number of trains, sometimes
  night), and a diff of it would mean nothing.
- **Each shot waits for the map to be idle**, not for a fixed number of
  milliseconds. `waitForMapIdle()` polls `map.loaded() && map.areTilesLoaded()`.
  The first version of the script used a three-second sleep and the hero image
  came out with the 3D network floating over a blank page, because jumping to a
  new zoom level starts a fresh round of vector-tile requests. A screenshot of a
  half-loaded map is a screenshot of a bug that does not exist.
- **The street-level shot is framed from the vehicle buffer**, not from a
  landmark. Aiming at a scenic junction and hoping a train is passing produced a
  beautiful photograph of Siam with no train in it. The subject of that frame is
  the rolling stock, so the camera position comes from a vehicle that is
  actually in transit.
- **Two viewports.** Desktop is 1600 × 900 at DPR 2; the phone shots are
  390 × 844 at DPR 3, in Thai, because "it works on a phone" and "it works in
  Thai" are the two claims most worth showing rather than asserting.

## Why the video is built the way it is

- **Frames come from CDP `Page.startScreencast`, and each frame keeps its own
  timestamp.** A screencast does not deliver at a fixed rate — it skips while
  the renderer is busy and bursts when it is not — so assembling frames at an
  assumed frame rate yields a video that speeds up and slows down against
  reality. The frames go into an ffmpeg concat list with their *real* durations
  and ffmpeg resamples that to constant 30 fps. Headless rendering here is CPU
  (SwiftShader), so capture can run slower than real time; because pacing comes
  from timestamps, that shows up as a lower frame rate, never as the wrong
  speed.
- **Camera moves use the map's own `easeTo`/`flyTo`.** Stepping a camera from
  outside, frame by frame, does not match what a user sees when they interact
  with the app — and the point of a demo video is to show what the app does.
- **Captions are injected by the script**, into a `pointer-events: none`
  overlay, and are re-created on every call. They are part of the video, not
  part of the app. The idempotence is not tidiness: a run that installed the
  helper once died four scenes in with `window.__caption is not a function`, and
  a recording that throws two thirds of the way through is a recording thrown
  away.
- **MP4 only, and deliberately not a master.** H.264 in `yuv420p` plays inline
  in GitHub's own player, in every browser in the support matrix, and on iOS.
  A first cut at CRF 21 came to 47 MB for 91 seconds — a fine master and a bad
  repository asset, so it is CRF 27 now. A second 30 MB WebM encode of the same
  91 seconds would earn the repository nothing, so there isn't one.
- **The GIF is short on purpose.** GitHub autoplays a GIF but needs a click to
  play a video, so the first thing a visitor sees should move by itself. It is
  the opening orbit only, 10 fps at 640 px. A full-length GIF of this runs to
  tens of megabytes, and a README that takes 18 MB to open is worse than one
  with a still image.

## Do not hand-edit `docs/media/`

Anything you change there will be overwritten by the next run, and the
difference between a generated and a retouched screenshot is exactly the kind of
thing nobody can spot later. If a shot is wrong, change the script that makes
it — `tools/make-media.mjs` or `tools/make-video.mjs`.

The same rule applies, more strictly, to `public/promptpay-qr.svg`: it is
generated by `npm run qr` and a unit test
(`tools/support.test.mjs`) fails if it stops matching the configured account.
